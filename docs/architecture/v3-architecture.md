# สถาปัตยกรรมระบบ V3

> อัปเดตล่าสุด: 19 ตุลาคม 2026 · ใช้กับ V3 – Secure Collaboration Workspace (โจทย์ที่ 7)

V3 เพิ่มการเข้าสู่ระบบ ผู้ใช้ 5 บทบาท และการแก้ไขข้อมูลผ่านหน้าเว็บตามสิทธิ์ของแต่ละบทบาท
บนโครงสร้างเดียวกับ V2 (Amplify + EC2 + RDS + S3) ส่วนที่เพิ่มคือ **Amazon Cognito** สำหรับบัญชีผู้ใช้
และ **ตาราง `audit_logs`** สำหรับประวัติการแก้ไข

ข้อกำหนดของ V3 ตามเอกสารรายวิชา: ระบบต้องรองรับการเข้าสู่ระบบและผู้ใช้หลายบทบาท ผู้ประสานงาน เจ้าหน้าที่ นักศึกษา
และผู้บริหารเข้าถึงหรือดำเนินการกับข้อมูลตามสิทธิ์ รวมถึงเอกสาร ข้อมูลส่วนบุคคล สถานะของข้อตกลง และข้อมูลการแลกเปลี่ยนนักศึกษา

## ส่วนประกอบหลัก

| ส่วน | บริการ | หน้าที่ใน V3 |
|---|---|---|
| หน้าเว็บ | **AWS Amplify Hosting** | Next.js เก็บ access token ใน `sessionStorage` แล้วส่งเป็น `Authorization: Bearer` ทุกคำขอ ซ่อนปุ่มตามบทบาท (เพื่อความสะดวกเท่านั้น) |
| บัญชีผู้ใช้ | **Amazon Cognito** user pool `cstu-v3-auth` | เก็บรหัสผ่าน ตรวจรหัสผ่าน ออก token อายุ 60 นาที บทบาทมาจากกลุ่ม (`cognito:groups`) |
| API | **FastAPI ใน Docker บน EC2** (`CS361-ec2`) | ตรวจ token ด้วย JWKS ของ Cognito, ตรวจสิทธิ์ทุก endpoint ด้วย `require_role(...)`, บันทึกประวัติการแก้ไข |
| ฐานข้อมูล | **RDS PostgreSQL** (`cs361-partner-db`, database `cstu_demo`) | ข้อมูลเดิมของ V2 + ตาราง `users`, `revoked_tokens`, `audit_logs` และคอลัมน์เจ้าของรายการ (`owner_user_id`) |
| ไฟล์ข้อตกลง | **S3** (`cs361-partner-docs`) | ไฟล์ PDF ที่อัปโหลดผ่านเว็บ ดาวน์โหลดไฟล์ภายในผ่านลิงก์อายุ 5 นาที |

ทุกบริการอยู่ใน region **ap-southeast-1 (Singapore)**

## ข้อมูลวิ่งอย่างไร

1. **เข้าสู่ระบบ:** เว็บส่งอีเมลและรหัสผ่านไปที่ `POST /api/v1/auth/login`
   backend ส่งต่อให้ Cognito ตรวจ (`USER_PASSWORD_AUTH`) แล้วสร้างหรืออัปเดตแถวในตาราง `users`
   (อีเมล บทบาท เวลาเข้าสู่ระบบล่าสุด) **รหัสผ่านไม่ถูกเก็บในฐานข้อมูลของระบบ**
2. **ทุกคำขอหลังจากนั้น** มี access token แนบไปด้วย backend ตรวจลายเซ็นกับ public key ของ Cognito (JWKS)
   ตรวจว่า token ยังไม่หมดอายุและยังไม่ถูกยกเลิก (`revoked_tokens`) แล้วอ่านบทบาทจากกลุ่มใน Cognito
3. **ตรวจสิทธิ์ที่ backend เสมอ:** ทุก endpoint ที่เขียนข้อมูลใช้ `require_role(...)`
   และรายการที่เป็น "ของตัวเอง" ตรวจ `owner_user_id` (หรือ `user_id` สำหรับนักศึกษาแลกเปลี่ยน)
   ไม่มี token ได้ 401, บทบาทไม่พอได้ 403 หน้าเว็บแสดงข้อความภาษาไทยตามรหัสนี้
4. **ทุกการแก้ไข** บันทึกแถวใน `audit_logs` (ใคร ทำอะไร กับรายการไหน ค่าก่อน-หลัง)
   ใน transaction เดียวกับการแก้ข้อมูล รหัสผ่านและ token ไม่ถูกบันทึก
5. **ไฟล์ข้อตกลง:** อัปโหลดผ่าน `PUT /documents/{id}/file` (PDF ไม่เกิน 10 MB) ขึ้น S3
   ไฟล์ของข้อตกลงที่ยังไม่เผยแพร่เปิดได้ผ่านลิงก์ที่ backend สร้าง อายุ 5 นาที
6. **ออกจากระบบ:** `POST /auth/logout` บันทึก token ลง `revoked_tokens` token เดิมใช้ไม่ได้ทันที
   แม้ยังไม่หมดอายุ

## บทบาทและสิทธิ์

รายละเอียดเต็มอยู่ใน [สิทธิ์ตามบทบาทของ V3](../decisions/v3-role-permissions.md) สรุป:

| บทบาท | ทำอะไรได้ |
|---|---|
| ผู้ใช้ทั่วไป (`public`) | ดูข้อมูลที่เผยแพร่ เหมือนผู้ที่ยังไม่เข้าสู่ระบบ |
| นักศึกษา (`student`) | ดูข้อมูลการแลกเปลี่ยนที่เชื่อมกับบัญชีตัวเองเท่านั้น |
| อาจารย์ผู้ประสานงาน (`coordinator`) | เพิ่มและแก้ไขหน่วยงาน ข้อตกลงฉบับร่าง กิจกรรม และข้อมูลการแลกเปลี่ยน **ของตัวเอง** เผยแพร่เองไม่ได้ |
| เจ้าหน้าที่หลักสูตร (`staff`) | แก้ไขทุกรายการ อนุมัติ เปลี่ยนสถานะ ตรวจความเกี่ยวข้องกับ CSTU เผยแพร่ ลบ ดูประวัติการแก้ไข |
| ผู้ดูแลระบบ (`admin`) | ทุกอย่างของเจ้าหน้าที่ และดูรายชื่อบัญชีผู้ใช้ |

หลักที่ใช้:
- **คนสร้างไม่ใช่คนอนุมัติ:** ข้อตกลงเดินตาม `ฉบับร่าง → อนุมัติแล้ว → มีผล → หมดอายุ` (ยกเลิกได้)
  อาจารย์สร้างฉบับร่างได้ แต่อนุมัติและเผยแพร่ได้เฉพาะเจ้าหน้าที่
- **หน้าสาธารณะแสดงเฉพาะข้อตกลงที่เผยแพร่และเกี่ยวข้องกับ CSTU** (`cstu_status = keep`)
- **ไม่ลบจริง:** การลบเป็น soft delete ข้อมูลยังดูได้ในประวัติการแก้ไข
- **ข้อมูลส่วนบุคคลของนักศึกษา** ส่งให้เฉพาะเจ้าของบัญชี อาจารย์ที่บันทึก และเจ้าหน้าที่

## ทำไมเลือกแบบนี้ และทางเลือกที่พิจารณา

| เรื่อง | เลือก | ทางเลือกอื่น | เหตุผล |
|---|---|---|---|
| บัญชีและรหัสผ่าน | **Amazon Cognito** | เก็บ bcrypt + ออก JWT เอง | ไม่ต้องเก็บรหัสผ่านเอง ได้ password policy, การล็อกเมื่อลองผิดหลายครั้ง และการยกเลิก token จาก AWS ข้อเสียคือผูกกับ AWS และเพิ่ม/เปลี่ยนบทบาทต้องทำใน Cognito |
| ที่ตรวจสิทธิ์ | **backend ทุก endpoint** | ซ่อนปุ่มที่หน้าเว็บอย่างเดียว | หน้าเว็บถูกข้ามได้ด้วยการเรียก API ตรง เทสต์ `test_v3_combined.py` ตรวจว่า endpoint เขียนข้อมูลทุกตัวต้องเข้าสู่ระบบ |
| บทบาทเก็บที่ไหน | **กลุ่มใน Cognito** และสำเนาในตาราง `users` | ตาราง role ของระบบเอง | แหล่งความจริงเดียว บทบาทในตารางอัปเดตจาก token ทุกครั้ง |
| ประวัติการแก้ไข | **ตาราง `audit_logs` ใน RDS** | CloudTrail / CloudWatch Logs | ต้องเก็บค่าก่อน-หลังระดับรายการ และให้เจ้าหน้าที่ค้นได้ผ่าน API |
| token บนหน้าเว็บ | **`sessionStorage`** | cookie HttpOnly | ปิดแท็บแล้วหมด ไม่ต้องจัดการ CSRF ข้อเสียคือสคริปต์บนหน้าอ่านได้ จึงต้องระวัง XSS |
| วิธี deploy backend | **Docker บน EC2 เดิม** (Instance Connect) | ECS/Fargate, Lambda | ไม่เพิ่มค่าใช้จ่าย ทีมคุ้นเคย เป็นจุดที่จะทำเป็นอัตโนมัติใน V5 |

## การ deploy V3 (19 ตุลาคม 2026)

1. สร้าง RDS snapshot `cs361-before-v3-20261019` ก่อนแก้ฐานข้อมูล
2. ดึงโค้ด backend จาก GitHub ขึ้น `CS361-ec2` (เก็บโค้ด V2 ไว้ที่ `~/cs361/backend.v2` สำหรับย้อนกลับ)
3. เพิ่ม `COGNITO_REGION`, `COGNITO_USER_POOL_ID`, `COGNITO_APP_CLIENT_ID` ใน `.env` บนเครื่อง
4. รัน `python migrate_v3.py` กับ RDS (เพิ่มตารางและคอลัมน์ ไม่ลบข้อมูลเดิม รันซ้ำได้)
5. `docker compose up -d` แล้วตรวจ `/health` = 200 และ `/auth/me` = 401
6. merge PR #82 เข้า `main` Amplify build และ deploy frontend ให้เอง

**ย้อนกลับ:** สลับ `backend` กับ `backend.v2` แล้ว `docker compose up -d --build`
migration เป็นการเพิ่มอย่างเดียว V2 ใช้ฐานข้อมูลเดิมต่อได้ ถ้าจำเป็นกู้ฐานข้อมูลจาก snapshot

## ข้อจำกัดที่ควรรู้

- **เพิ่มบัญชีหรือเปลี่ยนบทบาทต้องทำใน Cognito** (console หรือ `infra/provision_cognito.py`)
  หน้า "ผู้ใช้และสิทธิ์" บนเว็บดูได้อย่างเดียว เพราะการแก้ Cognito จากเว็บต้องให้ backend มีสิทธิ์ IAM เพิ่ม
- **ผู้ใช้เปลี่ยนรหัสผ่านตัวเองได้** ที่หน้า "ตั้งค่าบัญชี" แต่ลืมรหัสผ่านต้องให้ผู้ดูแลระบบรีเซ็ตใน Cognito
- **ความคิดเห็นและรายงาน** ทำไว้แล้วทั้ง API และหน้าเว็บ แต่ซ่อนไว้สำหรับ V4 (Stakeholder Insight)
- **การต่ออายุข้อตกลง** ยังทำโดยแก้ข้อมูลฉบับเดิม การสร้างฉบับใหม่ที่เชื่อมกับฉบับเดิมเป็นงาน V4
- ข้อจำกัดเดิมของ V2 ยังอยู่: backend มีเครื่องเดียว IP ของ EC2 ไม่ถาวร ไม่มี Multi-AZ
