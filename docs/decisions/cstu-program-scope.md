# ขอบเขตระบบความร่วมมือของ CSTU

สถานะ: ตกลงกับผู้ใช้วันที่ 2 ตุลาคม 2026 (Asia/Bangkok)

## เป้าหมาย

ระบบกลางสำหรับจัดเก็บและติดตามความร่วมมือของหลักสูตรวิทยาการคอมพิวเตอร์
มหาวิทยาลัยธรรมศาสตร์ โดยเริ่มที่ระดับปริญญาตรี ศูนย์รังสิต
มีหน้าสาธารณะเผยแพร่ข้อมูลที่อนุญาต และพื้นที่ภายในสำหรับผู้รับผิดชอบ
จัดการข้อมูลตามสิทธิ์

ขอบเขตนี้จำกัดหน่วยงานและกลุ่มผู้ใช้ที่ระบบดูแล แต่ยังพัฒนาความสามารถ
ตามข้อกำหนดของโจทย์ที่ 7 และลำดับ V1–V7 ไม่ได้ตัดข้อกำหนดปลายทางออก
ชื่อ CSTU ในเอกสารนี้หมายถึงขอบเขตข้างต้น ไม่ใช่ทุกหลักสูตรหรือทุกศูนย์
ของมหาวิทยาลัย

## ผู้ใช้และข้อมูล

- ผู้ใช้ทั่วไป: ดูข้อมูลที่อนุญาตให้เผยแพร่
- นักศึกษา/ผู้เข้าร่วม: ดูและดำเนินการกับข้อมูลที่เกี่ยวข้องกับตนตามสิทธิ์
- อาจารย์/ผู้ประสานงาน: บันทึกและติดตามความร่วมมือที่รับผิดชอบ
- เจ้าหน้าที่หลักสูตร: ดูแลข้อมูล เอกสาร สถานะ และข้อมูลสรุป
- ผู้บริหาร/ผู้ดูแลระบบ: ดูผลลัพธ์และ Feedback รวมถึงจัดการสิทธิ์ที่ได้รับมอบหมาย

ข้อมูลหลักครอบคลุม Stakeholder ทั้งหน่วยงานและบุคคล ผู้ประสานงาน
ข้อตกลง กิจกรรม ผลลัพธ์/หลักฐาน การแลกเปลี่ยนนักศึกษา และ Feedback
ความสัมพันธ์หลักคือ Stakeholder → ข้อตกลง/ความร่วมมือ → กิจกรรมหรือ
การแลกเปลี่ยน → ผลลัพธ์และ Feedback → ข้อมูลสรุปสำหรับพัฒนาหลักสูตร
กิจกรรมไม่จำเป็นต้องมี MoU และ Stakeholder ไม่จำเป็นต้องเป็นหน่วยงาน

## เกณฑ์นำข้อมูลเข้าขอบเขต

1. ต้องมีหลักฐานระบุความเกี่ยวข้องกับ CSTU ในขอบเขตที่ตกลง เช่น
   CSTU เป็นผู้จัด/ผู้ร่วมดำเนินการ เป็นหน่วยงานในข้อตกลง หรือมีนักศึกษา
   ของหลักสูตรเข้าร่วมในบริบทความร่วมมือนั้น
2. ข้อตกลงระดับคณะหรือมหาวิทยาลัยใช้ได้เมื่อมีหลักฐานว่าครอบคลุม CSTU
   ต้องแยกผู้ลงนาม/เจ้าของข้อตกลงออกจากหลักสูตรที่ได้รับประโยชน์
   ห้ามเปลี่ยนชื่อเจ้าของข้อตกลงให้เป็น CSTU
3. ข่าวที่กล่าวถึงธรรมศาสตร์อย่างเดียว หรือความร่วมมือของสาขาอื่นอย่างเดียว
   ยังไม่เพียงพอที่จะนับเป็นความร่วมมือของ CSTU
4. เก็บแหล่งข้อมูลและหลักฐานความเกี่ยวข้องเพื่อให้ตรวจสอบย้อนหลังได้
   หากยังยืนยันไม่ได้ ให้รอทบทวนก่อนนับหรือเผยแพร่ในขอบเขต CSTU
5. แยกการตรวจความเกี่ยวข้องกับ CSTU ออกจากการอนุญาตเผยแพร่
   ข้อมูลส่วนบุคคลและเอกสารภายในต้องเข้าถึงตามสิทธิ์

ข้อมูลจากแหล่งสาธารณะใช้เป็นจุดเริ่มต้นได้ ข้อมูลตัวอย่างสำหรับทดสอบ
ต้องระบุว่าเป็น synthetic และไม่อ้างว่าเป็นความร่วมมือจริง

## ลำดับการพัฒนา

| Version | ความสามารถในขอบเขต CSTU |
| --- | --- |
| V1 | หน้าสาธารณะสำหรับข้อมูลที่อนุญาตให้เผยแพร่ |
| V2 | จัดเก็บและเรียกข้อมูลจากแหล่งที่ดูแลได้อย่างเป็นระบบ ค้นหา/กรอง ดูรายละเอียด ความสัมพันธ์ และเอกสาร |
| V3 | การยืนยันตัวตน สิทธิ์ที่ตรวจจากฝั่งเซิร์ฟเวอร์ การจัดการข้อมูล/เอกสาร สถานะข้อตกลง และการแลกเปลี่ยนตามสิทธิ์ |
| V4 | ผลลัพธ์และ Feedback หลายแหล่ง การรับข้อมูลจากระบบอื่น และข้อมูลสรุป พร้อมพิจารณาความพร้อมใช้งานเมื่อการใช้งานเพิ่มขึ้น |
| V5 | สร้างและปรับใช้ infrastructure/deployment ซ้ำด้วย automation หรือ IaC |
| V6 | วัดและปรับปรุง critical path พร้อมหลักฐานก่อน–หลังและผลกระทบด้านต้นทุน |
| V7 | บูรณาการข้อมูลและผลลัพธ์ ทบทวน security, privacy, availability, scalability, performance และ cost |

การรับข้อมูลจากระบบอื่นอาจเริ่มด้วยไฟล์นำเข้า/ส่งออกที่ตรวจสอบได้
การเลือก API หรือวิธีอื่นต้องมีเหตุผลจากความถี่ ลักษณะข้อมูล สิทธิ์
และข้อจำกัดจริง ไม่จำเป็นต้องสร้างระบบสหกิจทั้งระบบขึ้นใหม่

## สถานะปัจจุบันและงานถัดไป

แนวทางสาธิตที่ตกลงเพิ่มเติมวันที่ 2 ตุลาคม 2026: ใช้ข้อมูลสมมติเป็นชุดหลัก
สำหรับนำเสนอ V2 ผ่าน API/PostgreSQL จริงใน `cstu_demo` แยกจากข้อมูลจริงเดิม
พร้อมป้ายระบุว่าเป็นข้อมูลสมมติ ดู [คู่มือเดโม](../demo-fictional.md)
ชุดเดโมเพิ่มบุคคลประเภทศิษย์เก่าและผู้เชี่ยวชาญผ่านโมเดล Stakeholder เดิม
ไม่ถือว่าได้ทำระบบจัดการบุคคลหรือพื้นที่ภายใน V3 ครบ
ความเกี่ยวข้องกับ CSTU ของข้อมูลจริงยังต้องตรวจตามเกณฑ์เดิม

เวอร์ชัน deploy ปัจจุบันเปิดเฉพาะหน้าสาธารณะของ V2: ภาพรวม หน่วยงาน
เอกสาร และกิจกรรม พื้นที่ภายในและสิทธิ์จริงยังไม่ได้เปิดใช้งาน
โมเดล Stakeholder ปัจจุบันเน้นหน่วยงาน ส่วนบุคคลเป็นงานที่ต้องต่อยอด

การตกลงขอบเขตและปรับข้อความหน้าเว็บครั้งนี้ไม่ได้ตรวจรับข้อมูลเดิม
ไม่ได้ยืนยันว่าทุกรายการสัมพันธ์กับ CSTU และไม่ได้เพิ่มตัวกรองหลักสูตร
ในฐานข้อมูล/API เกณฑ์ publication ปัจจุบันก็ยังไม่ตรวจความเกี่ยวข้อง
กับ CSTU จึงต้องทบทวนรายการเดิมและกำหนดวิธีเก็บหลักฐานความเกี่ยวข้อง
ก่อนอ้างว่าข้อมูลทั้งชุดอยู่ในขอบเขตนี้ครบถ้วน

งานลำดับต่อไป:

1. ตรวจข้อมูลเดิมเป็นรายรายการ พร้อมหลักฐานความเกี่ยวข้องกับ CSTU
   และสถานะคงไว้/รอทบทวน/อยู่นอกขอบเขต โดยรักษาประวัติข้อมูลเดิม
2. ระบุวิธีเพิ่ม/แก้/นำเข้าข้อมูล V2 ผู้รับผิดชอบ และขั้นตอนตรวจเผยแพร่
3. ออกแบบ Stakeholder บุคคลและผู้ประสานงานให้รองรับโจทย์
4. แตกงาน V3 เป็นกระบวนการที่ตรวจได้จริง เช่น บันทึกข้อตกลง
   อัปเดตสถานะและจัดการการแลกเปลี่ยนตามสิทธิ์
5. เชื่อมข้อกำหนดกับ issue การเปลี่ยนแปลง และหลักฐานของแต่ละเวอร์ชัน
