# Usability test plan — PCSMS

> เป้าหมาย: ทดสอบกับ **ผู้ใช้จริงอย่างน้อย 3 คน จากอย่างน้อย 2 roles** ตามใบโจทย์  
> เอกสารนี้เป็นแผนและเครื่องมือทดสอบ ไม่ใช่ผลการทดสอบจริง

## 1. วัตถุประสงค์

- วัดว่าผู้ใช้บทบาทจริงทำงาน TC1 และ TC2 ได้สำเร็จด้วยตนเองหรือไม่
- ระบุจุดที่ต้องได้รับความช่วยเหลือ ความสับสน และข้อผิดพลาด
- รวบรวมข้อเสนอแนะสำหรับการนำระบบไปใช้จริง
- ยืนยันว่าฟลว์สาธารณะ/นักศึกษาง่าย และฟลว์จัดการของเจ้าหน้าที่ซับซ้อนเพียงใด

## 2. ผู้เข้าร่วม

| กลุ่ม | จำนวนแนะนำ | เกณฑ์ |
|---|---:|---|
| Student | 2 | นักศึกษาที่ตรงบทบาท และไม่เคยใช้ระบบนี้ |
| Staff หรือ Coordinator | 2 | เจ้าหน้าที่/อาจารย์ผู้ประสานงานที่ตรงบทบาท |
| รวม | 4 | ขั้นต่ำ 3 คน จาก 2 roles |

ถ้าเวลาไม่พอ: 2 students + 1 staff/coordinator ก็ผ่านเกณฑ์ขั้นต่ำ แต่แนะนำ 2+2 เพื่อเทียบความต่างภายใน role

## 3. TC1 / TC2

> **หมายเหตุ:** ต้องใช้ TC1/TC2 จากใบโจทย์ของอาจารย์เป็นหลัก  
> ด้านล่างเป็นฉบับร่างสำหรับระบบ PCSMS หากใบโจทย์ต่าง ให้แทนที่ข้อความแต่โครงสร้างและ success criteria ใช้แบบเดียวกันได้

### TC1 — Student/Public: ค้นหาและตรวจสอบความร่วมมือ

**สถานการณ์ (อ่านให้ผู้ใช้ฟัง):**
> “คุณเป็นนักศึกษาที่ต้องการทราบว่าหลักสูตรมีความร่วมมือกับหน่วยงานหนึ่งอย่างไร ขอให้ค้นหาหน่วยงานนั้น เปิดข้อตกลงที่เกี่ยวข้อง เปิดกิจกรรมที่เชื่อมโยง และดาวน์โหลดไฟล์ข้อตกลงถ้ามี”

**เป้าหมาย:** หาหน่วยงาน → ข้อตกลง → กิจกรรม → ดาวน์โหลด PDF  
**เริ่มที่:** `/dashboard/public` หรือ `/login` ด้วยบัญชี student  
**สำเร็จเมื่อ:** เปิดหน่วยงานถูกต้อง, เปิดข้อตกลงที่เกี่ยวข้อง, เปิดกิจกรรมที่เชื่อมโยง, ดาวน์โหลด PDF ได้ (หรืออธิบายได้ว่าทำไมไม่มีไฟล์)

### TC2 — Staff/Coordinator: บันทึกและเผยแพร่กิจกรรม

**สถานการณ์:**
> “คุณเป็นเจ้าหน้าที่หลักสูตร ต้องการบันทึกกิจกรรมใหม่ที่จัดร่วมกับหน่วยงานหนึ่ง และเชื่อมกับข้อตกลงที่มีอยู่ จากนั้นตรวจสอบว่ารายการนี้ปรากฏในหน้าสาธารณะ”

**เป้าหมาย:** สร้างกิจกรรม → เลือกหน่วยงาน → เชื่อมข้อตกลง → บันทึก → เผยแพร่ → ตรวจหน้าสาธารณะ  
**เริ่มที่:** `/dashboard/staff` หรือ `/dashboard/coordinator`  
**สำเร็จเมื่อ:** กิจกรรมถูกสร้าง, เชื่อมหน่วยงาน/ข้อตกลงถูกต้อง, เผยแพร่แล้ว, และเห็นในหน้าสาธารณะ

### TC2 ทางเลือก (ถ้าใบโจทย์เน้น V4)

- **Feedback:** ส่งความคิดเห็น → เจ้าหน้าที่ตอบกลับ/ตรวจสอบ → บันทึกการปรับปรุง
- **Import:** ดาวน์โหลด template → เตรียมไฟล์ → upload → preview → confirm

## 4. กำหนดการต่อคน (60 นาที)

| นาที | กิจกรรม |
|---:|---|
| 0–5 | ต้อนรับ, consent, ขออนุญาตบันทึก |
| 5–10 | ถามพื้นฐาน: บทบาท, ประสบการณ์ระบบสารสนเทศ, งานที่ทำบ่อย |
| 10–35 | ทำ TC1 และ TC2 (คิดออกเสียงได้) |
| 35–45 | ถามย้อนหลัง: จุดติดขัด, ความคาดหวัง, ข้อเสนอแนะ |
| 45–55 | SEQ หลังแต่ละ task + SUS 10 ข้อ |
| 55–60 | ปิด, ขอบคุณ, เก็บเอกสาร |

## 5. กติกาการดูแล (สำคัญ)

- อ่านสถานการณ์และเป้าหมายเท่านั้น **ห้ามบอกขั้นตอนหรือชี้ปุ่ม**
- ใช้คำถามกลาง เช่น:
  - “ตอนนี้คิดอะไรอยู่ครับ/คะ”
  - “ลองทำต่อตามที่คิดว่าควรทำ”
  - “ถ้าติดตรงนี้ จะทำอย่างไรต่อ”
- ถ้าผู้ใช้เงียบเกิน 30 วินาที ให้ถาม “ต้องการความช่วยเหลือไหมครับ/คะ” แล้วบันทึก
- บันทึกความช่วยเหลือเป็นระดับ:
  - **0** = ทำเองทั้งหมด
  - **1** = verbal hint (บอกใบ้คำ)
  - **2** = direct instruction (บอกขั้นตอน)
  - **3** = ทำแทน
- ห้ามสอนระหว่าง task; ถ้าต้องสอน ให้จบ task และบันทึกว่าล้มเหลว/ต้องช่วย

## 6. ตัวชี้วัด

| ตัวชี้วัด | วิธีเก็บ |
|---|---|
| Success | สำเร็จ / สำเร็จบางส่วน / ไม่สำเร็จ |
| Time on task | จับเวลาตั้งแต่จบคำสั่งจนถึงเป้าหมาย |
| Errors | จำนวนครั้งที่กดผิด/เลือกผิด/ย้อนกลับ |
| Assistance | ระดับ 0–3 ตามด้านบน |
| SEQ | 1–7 หลังแต่ละ task |
| SUS | 10 ข้อท้าย session |
| Quotes | คำพูดของผู้ใช้ที่สะท้อนปัญหาหรือความพอใจ |

- Accounts: `student@example.test`, `staff@example.test`, `coordinator@example.test`, `admin@example.test` (รหัสผ่านดูจาก operator)

## 8. การวิเคราะห์

- จัดกลุ่มปัญหาตามความถี่ (กี่คนเจอ) × ความรุนแรง (blocker / major / minor)
- แยกตาม role และ task
- สรุปเป็น:
  1. จำนวนคนที่สำเร็จเอง
  2. จุดที่ต้องช่วยมากที่สุด
  3. ข้อเสนอแนะที่ทำได้จริง
  4. สิ่งที่ควรแก้ก่อนใช้งานจริง
